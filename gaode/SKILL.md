# 周边去哪儿（高德地点推荐）

一次任务只做一件事：**从同一个起点出发，给出最多 3 个真实、可步行到达的地点备选**，每个都附高德返回的步行距离与耗时。

## 什么时候用

- 用户问"附近有什么…""推荐几家…""步行 15 分钟内能到的…"，起点是坐标、地铁站、商场或地址。
- 只做单点周边的独立备选推荐。多站行程串联、驾车/公交方案、跨城出行不属于本 Skill。

## 一、先解析需求（不要跳过）

从用户一句话里抽取下表 6 项，缺的按缺省值补：

| 要素 | 取法 | 缺省 |
| --- | --- | --- |
| 城市 | 用户明确说的城市 | 以起点坐标所在城市为准 |
| 起点 | 优先用给定坐标；给的是地名时先做地理编码 | 没有起点就先问一次 |
| 地点类型 | "咖啡""餐厅""公园"等具体类型词 | 无 |
| 步行时间上限 | "步行不超过 15 分钟"→15 分钟 | 不限，但仍要报步行时间 |
| 推荐数量 | "最多 3 家"→3 | 3 |
| 偏好 | 近 / 评分高 / 安静 / 适合办公 | 按步行距离升序 |

**明确条件（数量、步行时间上限、类型）是硬约束，任何情况下不能突破。** 模糊偏好（安静、人少、环境好）只影响排序和措辞，不能变成"事实"。

## 二、查地点：工具调用顺序

工具名以当前环境实际提供的为准；名称不同时按能力对应（地理编码 / 周边搜索 / 关键字搜索 / 步行路径规划）。

1. **确定起点坐标**
   - 用户已给"经度,纬度"→ 直接用，不要重新编码。
   - 只给地名、地铁站、商场、地址 → 用地理编码（`maps_geo`，参数 `address` + `city`），取第一条结果的坐标，统一成"经度,纬度"。
   - 编码失败或结果为空：请用户补充更具体的起点；若必须继续，用用户给的区域中心并明确写"起点为近似位置"。

2. **周边搜索**（`maps_search_around`）
   - `keywords` 传类型词（"咖啡""餐厅""公园"），`location` 传起点坐标，`radius` 传半径（米），需要时用 `types` 收窄类别。
   - 半径按下式估算：用户给了步行时间上限 T 分钟时，`radius ≈ T × 80` 米（15 分钟 ≈ 1200 米），最小 500、最大 3000。
   - 结果为空或明显偏少：半径放宽到 1.5 倍再搜一次，同一次任务最多放宽两次；仍为空就进入"无结果"处理。
   - 类型词不理想时可退一步用关键字搜索（`maps_text_search`，`keywords` + `city`），但结果仍以起点为圆心重新筛距离。

3. **候选预筛**（省调用、提准确率）
   - 剔除类别明显不符的条目（搜咖啡却返回银行、加油站）、没有坐标的条目、明显不在同一片区的条目。
   - 按到起点的直线距离升序，取前 6–8 个进入路线查询；不要对全部搜索结果逐个调路线。

4. **步行路线**（必须逐个查，不能用直线距离替代）
   - 对每个候选调步行路径规划（`maps_direction_walking`）：`origin` = 起点坐标，`destination` = 候选坐标。
   - 返回结构是 `origin` / `destination` / `paths`：距离和耗时在 `paths[0].distance`（米）和 `paths[0].duration`（秒）里。字段可能是数字、也可能是字符串，先转成数字再算；多段时取 `paths` 里的总路径，不要自己把 `steps` 加起来。
   - 秒 ÷ 60 向上取整，报"约 X 分钟"。不要拿骑行、驾车接口的 `distance`/`duration` 冒充步行数据。
   - 拿不到路线（报错、空路径、缺 `distance`/`duration`）的候选不能算"符合条件"：剔除，并在说明里写"另有 N 个候选未取得步行路线，已排除"。
   - 每个候选都从**同一起点独立**计算，不要串成"先去 A 再去 B"。

5. **筛选与排序**
   - 硬筛选：步行耗时 ≤ 用户上限的候选才保留。
   - 排序：用户说"优先近一点/方便一点"→ 按步行距离升序（距离相同再看耗时）；用户说"评分高"→ 按高德返回的评分降序，并在理由里带上评分；无偏好时同样按步行距离升序。
   - 取前 N 个，N = 用户要的数量，**最多 3 个**。
   - 超出时间上限但用户可能感兴趣的候选，只能单独提一句"另有 X 步行约 Y 分钟，超出限制"，**不能混进推荐列表**。

调用示例（数值仅示意格式，实际以工具返回为准）：

```
maps_geo(address="龙翔桥地铁站", city="杭州")            → location "120.160,30.248"
maps_search_around(keywords="咖啡", location="120.160,30.248", radius=1200)
maps_direction_walking(origin="120.160,30.248", destination="120.163,30.250") → paths[0].distance 420, paths[0].duration 360
```

## 三、回答格式

先一句话给结论，再给表格，最后 1–2 句补充：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | XX咖啡（XX店） | XX市XX区XX路XX号 | 420 米 | 约 6 分钟 | 步行最短，评分 4.6，适合快速解决一杯 |
| 2 | … | … | … | … | … |

- 名称、地址照抄高德返回，不改写、不补全门牌号。
- 步行距离和时间来自路线查询，保留"约"字，单位用米 / 分钟。
- 推荐理由一句话，只引用已取得的数据（距离、时间、类别、评分、营业时间）；没有数据支撑的感受性描述一律标"未核实"。
- 表格后用一句话收口：覆盖范围（"3 家都在 12 分钟步行圈内"）或不足说明。
- 用用户的语言回答；用户说中文就用中文。

## 四、不足、异常与信息缺失（必须如实说）

- **结果不够**：符合条件只有 k 家（k 小于用户要的数量）时，推荐这 k 家，并说明"周边 X 米 / 步行 X 分钟内符合条件的只有 k 家"，再给放宽建议（扩大半径、放宽时间到 20 分钟、换类型）。
- **完全没有结果**：直接说"在 X 米范围内没有找到符合条件的<类型>"，写清实际用过的关键词和半径，给放宽建议。不要为凑数编地点。
- **工具失败或超时**：同一调用最多重试一次；仍失败就说明哪一步失败（地点搜索 / 步行路线）和"本次没有拿到可靠的步行数据"。已确认的地点可以列出，但必须标注缺路线数据的那几家。
- **信息缺失**：营业状态、排队情况、安静程度、是否适合办公、是否宠物友好等，没有工具依据就写"未核实"，不要推测。
- **绝对不能**：编造 POI、地址、评分、距离或耗时；用直线距离冒充步行距离；拿骑行/驾车路线顶替步行路线；把超时地点写成"符合条件"；承诺"一定营业""不用排队"。

## 五、提交前自检

- [ ] 数量 ≤ 用户要求，且 ≤ 3
- [ ] 每条都有名称、地址、步行距离、步行时间、一句理由
- [ ] 所有步行数据来自路线查询，且都不超过用户的时间上限
- [ ] 排序与用户偏好一致（说"优先近"就按步行距离升序）
- [ ] 结果不足、查询失败、未核实的地方都写了说明，没有任何编造
