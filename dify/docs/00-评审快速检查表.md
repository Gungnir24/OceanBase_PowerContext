# 00 · 评审快速检查表

给评审的 10 分钟路径。想直接开玩，跳到第 4 步。

---

## 1. 看作品（1 分钟）

- 创意与玩法：[`README.md`](../README.md) 第 1 节
- 技术分工：[`03-技术结合说明.md`](03-技术结合说明.md)
- 工作流本体：[`dsl/grudge-inn.yml`](../dsl/grudge-inn.yml)（8 节点，可在编辑器里直接看）

## 2. 验交付物完整性（1 分钟）

```bash
python tools/validate_dsl.py dsl/grudge-inn.yml
```

期望输出 `检查完成：0 个错误`。这一步会检查节点字段、连线、`{{#node.var#}}` 引用、`advanced-chat` 不允许 `end` 节点等导入硬约束。

## 3. 复现记忆闭环（3 分钟，不需要 Dify）

```bash
# 起 PowerContext（有 Docker 用这条）
docker compose -f docker/docker-compose.powercontext.yml up -d
curl http://127.0.0.1:18080/health/live

# 跑四轮对话 + 断言
python tools/smoke_test.py --base-url http://127.0.0.1:18080 --model stub
```

期望看到 `通过 6/6 项断言`，并生成 `evidence/logs/smoke-*.md`。
其中"换会话仍能翻出旧账"直接验证了跨会话记忆。

> `--model stub` 是确定性桩模型，只验证流程与记忆读写；想看拟人输出，加 `DEEPSEEK_API_KEY` 后换成 `--model deepseek`。

## 4. 在 Dify 里跑起来（5 分钟）

1. 导入 `dsl/grudge-inn.yml`
2. 填环境变量：`PC_BASE_URL`（Dify 在容器里用 `http://host.docker.internal:18080`）、`PC_SCOPE_ID`（`python tools/init_scope.py --base-url http://127.0.0.1:18080` 的输出）
3. LLM 节点绑定一个可用模型（推荐 `deepseek-chat`）
4. 发布 → 按 [`02-验证样例与证据.md`](02-验证样例与证据.md) 的四轮脚本对话

## 5. 三个必看的行为

| 看什么 | 怎么验 | 说明 |
| --- | --- | --- |
| 真的写进了 PowerContext | 对话后看 Dashboard `http://127.0.0.1:18080/dashboard/home`，或看 `记一笔账` 节点响应里的 `artifact_id` | 记忆不是模型现编的 |
| 真的跨会话 | 点「新对话」，问「老板，还认得我吗？」 | 账本按 Scope 存，与 `conversation_id` 无关 |
| 状态真的被复用 | 记仇值随恶作剧上升、随道歉下降；≥60 时老陈开始报复 | 数值由代码累加截断，不是模型随口说 |

## 常见判定问题

**Q：这不就是聊天机器人加了个记忆吗？**
记忆是玩法本身：账本是玩家行为的因果记录，记仇值直接决定 NPC 的攻击性，且跨会话累积。技术上是"事件流 + 状态外置"，不是把历史聊天记录塞进 prompt。

**Q：PowerContext 具体用在哪？**
三个真实 API：`context/prepare`（取回相关旧事）、`memory/entries/list`（翻账本还原状态）、`memory/remember`（写入本轮）。见 `03-技术结合说明.md` 第 3 节的参数表。

**Q：为什么不用官方 Dify 插件？**
官方 PowerContext 插件要求 Dify 1.17.1 + 插件守护进程，且不附带 DSL 模板，评审复现成本高。本作品改用内置 HTTP Request 节点，零插件依赖，导入即用。

**Q：seekdb 用了吗？**
按要求 PowerContext 或 seekdb 至少用一个，本作品用 PowerContext；同时给出 seekdb 作为其存储后端的部署方式（`docker/docker-compose.powercontext.yml` 的 `seekdb` profile）。Windows 本机无法跑嵌入式 seekdb，已在 README 的「已知限制」中说明。
