# 03 · 技术结合说明

本题的硬性要求是：**Dify 必须承担核心编排，seekdb 或 PowerContext 至少用一个，并真正发挥作用。**
本作品用 **PowerContext** 承载记忆；seekdb 作为 PowerContext 可切换的存储后端一并给出。

---

## 1. 总体架构

玩家

│                  ▼                   ▼                 ▼            │

│                  │                                                   │

## 2. Dify 做了什么（不是"套壳"，是核心流程）

| # | 节点 | 类型 | 职责 | 关键实现 |
| --- | --- | --- | --- | --- |
| ① | 开始 | start | 接收 `sys.query` | 不设必填输入，降低上手门槛 |
| ② | 取回旧日上下文 | HTTP | 调 `context/prepare`，取回预算内历史上下文 | 固定检索式（`玩家 老陈 客栈 账本 记仇 恶作剧 事件`），避免用户输入破坏 JSON 请求体 |
| ③ | 翻开账本 | HTTP | 调 `memory/entries/list`，取最近 100 条 | 全量账本，保证"记仇值"不丢 |
| ④ | 整理账本 | Code | 解析两个响应、按"第 N 笔"排序、还原记仇值、拼提示词素材 | 不依赖列表顺序（同秒写入顺序不稳定） |
| ⑤ | 老陈 | LLM | 角色扮演 + 输出结构化 JSON（reply/delta/summary/mood） | 关闭 Dify 会话记忆，记忆只来自 PowerContext |
| ⑥ | 记账 | Code | 解析模型 JSON（容错）、算新记仇值、生成写回请求体 | `json.dumps` 保证请求体合法 |
| ⑦ | 记一笔账 | HTTP | 调 `memory/remember` 写回 | 请求体由 ⑥ 生成，HTTP 节点只负责发送 |
| ⑧ | 回答 | answer | 输出台词 + `📒 第 N 笔账 ｜ 记仇值 X/100` | 让记忆状态对玩家可见 |

**为什么"整理账本/记账"用 Code 而不是让模型算？**
记仇值是游戏状态，必须可复现、可断言。模型只负责"给一个 −30~+40 的 delta"，累加、截断、编号、排序全部由代码完成——这样同一段对话在不同模型上跑，状态机的行为是一致的。

### 为什么 LLM 节点的 prompt 里只有 system

Dify 的 LLM 节点会把 `memory.query_prompt_template`（默认 `{{#sys.query#}}`）**作为最后一条 user 消息追加**到 messages 里。如果 DSL 的 `prompt_template` 里再写一条 `role: user / text: '{{#sys.query#}}'`，模型就会收到两条一模一样的用户输入。

实测后果：模型开始"接着上一句话说"，JSON 合规率从 16/16 掉到 1/5，账本数字不动，回答末尾还会出现两条账本行（模型自己在台词里补了一条）。

所以这份 DSL 的约定是：

- `prompt_template`：只放 system（人设 + 账本 + 输出协议）；
- `memory.query_prompt_template`：`'{{#sys.query#}}'`，由 Dify 追加，**不要在 prompt_template 里重复**；
- `memory.window.enabled: false`：不带 Dify 自己的历史对话，记忆只由 PowerContext 提供。

> 如果你要改这份 DSL：可以在 `prompt_template` 里加 system 段落，别加 user 段。

### 输出协议与兜底

模型被要求输出 `{"reply","delta","summary","mood"}` 四字段 JSON，协议单独成段并给了示例（见 DSL 里「输出协议」那一节）。实测 `deepseek-v4.1-flash` 在账本变长后仍会偶尔退化成纯文本，因此 `记账` 节点做了三层容错：

1. 先按 JSON 解析（含 ```json 围栏、JSON 混在文字里的情况）；
2. 解析不到就削掉模型自作主张写进来的 `📒 第 N 笔账` 尾行，避免和 answer 节点追加的那行重复；
3. 仍然拿不到 `delta` 时，用关键词兜底：道歉/请客/帮忙类 −12，换盐/教坏/赖账类 +12，其它 +2。

这样无论模型守不守规矩，记仇值都会动、账本都会长，玩起来不会"卡住"。

## 3. PowerContext 做了什么（记忆的唯一来源）

| 调用 | 时机 | 作用 | 实际参数 |
| --- | --- | --- | --- |
| `POST /v1/context/prepare` | 每轮开始 | 取回与"旧账"相关的历史上下文（检索 + 预算内装配），注入系统提示词 | `scope_id`、固定检索式、`max_bytes: 4000`、`explain: true` |
| `POST /v1/memory/entries/list` | 每轮开始 | 翻开最近 100 条账目，用于还原"第几笔 / 记仇值" | `scope_id`、`limit: 100` |
| `POST /v1/memory/remember` | 每轮结束 | 把本轮事件写回长期记忆 | `scope_id`、`kind: "event"`、`text`、`reason` |

### 记忆文本的约定

```
[第N笔｜记仇值 X/100] 玩家说：<玩家原话>；老陈：<一句话摘要>
```

- **第 N 笔**：单调递增的账本编号，既是给玩家看的"账本感"，也是代码还原状态时的排序键。
- **记仇值 X/100**：把游戏状态写进记忆文本，使"状态"与"记忆"同源——不需要额外的 KV 存储，PowerContext 就是唯一事实来源。
- **kind=event**：区分事件类记忆，后续若要扩展 `kind=letter`（道歉信）、`kind=promise`（承诺）可直接复用。

### 为什么能跨会话

Dify 的会话（`conversation_id`）只影响 Dify 自己的对话历史，而账本按 **Scope** 存储。新建会话只是换了一个 `conversation_id`，`scope_id` 不变，所以：

- 换会话 → 老陈照样认得你；
- 换浏览器 / 换设备 → 只要连同一个 PowerContext、同一个 Scope，账本还在；
- 想开新档 → 换一个 Scope 即可（`init_scope.py --reset`）。

### 为什么不用 Dify 知识库 / RAG

知识库是"文档 → 切片 → 向量检索"，适合静态资料；本作品需要的是**按时间累积、可增量写入、带状态的事件流**。PowerContext 的 Atomic Memory 正好是"一条一条可写入、可检索、可引用"的形态，而且天然按 Scope 隔离，比自建知识库更贴合"账本"这个隐喻。

## 4. seekdb 的分工

本题允许"PowerContext 或 seekdb 二选一"，本作品以 PowerContext 满足要求。同时给出 seekdb 路径，因为 PowerContext 的存储层本身可以落在 seekdb 上：

| 场景 | 存储层 | 启动方式 |
| --- | --- | --- |
| Windows 本机演示（已验证） | SQLite | `powercontext server run` |
| Linux / macOS 生产 | **seekdb**（嵌入式） | `docker compose --profile seekdb up -d powercontext-seekdb`，或 `pip install "powercontext[cli,server,seekdb]==1.4.1"` + `POWERCONTEXT_SERVER_DATABASE_KIND=seekdb` |

切换后，**应用层完全不用改**——Dify 里的三个 HTTP 调用、记忆格式、工作流都不变，账本从 SQLite 落到 seekdb 里。

> 诚实说明：本机是 Windows，嵌入式 seekdb 不可用，所以**已验证的是 SQLite 路径**；seekdb 路径给出的是部署配置与切换方法，未在本机实测。这一点在 README 的"已知限制"里也写了。

## 5. 失败与降级设计

| 失败点 | 行为 | 为什么这样设计 |
| --- | --- | --- |
| PowerContext 挂了 / 地址错 | HTTP 节点失败，工作流报错 | 宁可报错，也不要"假装还记得"——记忆是本作品的核心，静默降级会骗玩家 |
| `PC_SCOPE_ID` 为空 | 422，节点报错 | 配置错误应尽早暴露，文档里给了明确提示 |
| 模型不输出 JSON | `记账` 节点降级：直接播原文，本轮 delta=0 | 对话不中断，体验优先 |
| 模型输出越界 delta | 裁剪到 −30~+40，记仇值截断到 0~100 | 防止模型把游戏数值玩坏 |
| 同一秒写入多条记忆 | 按"第 N 笔"排序而非列表顺序 | 消除时序不确定性（这是实测踩到的坑） |
| 网络抖动 | 三个 HTTP 节点开启 `retry_enabled`（2 次，间隔 1s） | 轻量重试，避免瞬时失败 |
