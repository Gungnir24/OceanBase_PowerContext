# 验证样例：商品目录检索 —— 新增价格区间与库存筛选

本样例用来验证上下文模块是否真的「找到当前有效的规格、相关代码和测试」，并验证
「用 MiniMax 完成一次实际代码修改」后测试由失败转为通过。

---

## 1. 任务描述（要改什么）

```text
为 GET /api/products 增加按价格区间（price_min / price_max，单位元、闭区间、最多两位小数）
与库存状态（in_stock_only）的筛选条件；非法过滤参数返回 400 且错误码为 INVALID_FILTER；
过滤需与 keyword / sort / page / page_size 组合，total 为过滤后总数；
同时保持既有响应结构、排序语义与分页行为不变。
```

- 任务 ID：`T-2026-1028`
- 涉及接口：`GET /api/products`
- 业务工程：`workdir/biz/catalog/`（可独立启动，见第 7 节）

## 2. 哪些原有行为必须保持（不可改动）

| 项 | 要求 | 对应规格 |
| --- | --- | --- |
| 响应结构 | 固定 `items / total / page / page_size`；item 固定 `id/name/price/stock/category/tags`，`price` 为元（float） | COMPAT-003 |
| 关键字 | `keyword` 大小写不敏感子串匹配，命中商品名或 tag；空值不过滤 | COMPAT-001 |
| 排序 | `relevance`（种子顺序）/ `price_asc` / `price_desc` / `name_asc`；未知取值 400 `INVALID_SORT` | COMPAT-002 |
| 分页 | `page` 默认 1，`page_size` 默认 20、上限 100；非法值 400 `INVALID_PAGINATION`；越界返回空 items | COMPAT-004 |
| 测试文件 | 目标测试与回归测试**修改前后使用同一份**，不得删除断言 / skip / 改预期 | TEST-001、TEST-002 |

- 商品种子：`workdir/data/products.json`，20 个商品（含 5 个 `stock=0`）。

- 规格库：`data/specs/`（5 个文件、16 个条目）。

## 6. 操作步骤与预期结果

> 前置：seekdb（2881）与 PowerContext（8000）已启动，已 `pip install -r requirements.txt`。

### 步骤 0：初始化

```bash
python scripts/init_db.py
```

预期：`documents=16, clauses=16, chunks=105, symbols=78`（数字随代码演进会变，但都必须 > 0）。

### 步骤 1：装配上下文

```bash
python scripts/demo_context.py --task-id T-2026-1028
```

预期（核对待检查清单）：

- `## 1. 适用规格` 中出现 FILTER-001..004、COMPAT-001..004、ADR-0011、SRS-F-014；
- `## 5. 已失效 / 被取代的规格` 中出现 ADR-0007，并注明 `→ 由 ADR-0011 取代`；
- `## 2. 需要修改的代码` 至少包含 `service.py#search_products`、`filters.py`、`api.py#handle_products_query`；
- `## 3. 验证用测试` 同时包含 `test_search_target.py` 与 `test_search_regression.py`；
- `## 4. 任务状态（PowerContext）` 显示已完成 / 待办 / 已有验证结果；
- `## 6. 检索审计` 的 `run_id` 非空、命中数 > 0。

### 步骤 2：复现「修改前失败」

```bash
python scripts/replay_baseline.py
```

预期：目标测试 `14 failed, 3 passed`，回归测试 `14 passed`。
失败原因是 `assert 20 == 6` 这类**功能未实现**，不是缺依赖或起不来。

### 步骤 3：复现「修改后通过」

```bash
python scripts/replay_minimax.py --check
```

预期：`[3/4] 摘要校验：通过`、`[4/4] pytest：exit=0 passed=31 failed=0`。
摘要校验用的是 `docs/minimax/applied-digests.json`，即「当时 MiniMax 输出」的 sha256。

### 步骤 4：规格更新后上下文随之变化

```bash
python scripts/spec_update_demo.py
```

预期：

- 更新前 15 条（不含 FILTER-005），契约版本 2.3.0；
- 把契约升到 2.4.0 并新增 FILTER-005 后，条目 16 条，包含 FILTER-005；
- 恢复原规格后重新回到 15 条。

这一步证明上下文来自数据库检索，不是写死的答案。

### 步骤 5：状态复用（重启后读取）

```bash
python -m sddctx state show --task-id T-2026-1028 --json
python -m sddctx context --task "给 /api/products 加价格筛选" --task-id T-2026-1028 --json
```

预期：两条命令都是**新进程**，都能读到同一 `scope_id` 下的进展；
`context.json.state.done / todo / validations` 非空，且 `validations` 里带着 `exit_code` 与日志路径。

### 步骤 6：一键验收

```bash
python scripts/verify_all.py
```

预期：`验收结果：17/17 通过`，日志写入 `docs/logs/acceptance-<时间戳>.log`。

## 8. 重置方法

| 想重置什么 | 命令 |
| --- | --- |
| 业务代码回到修改前 | `python scripts/replay_baseline.py --restore` |
| 业务代码回到修改后 | `python scripts/replay_minimax.py --check` |
| seekdb 数据 | `python -m sddctx import --reset`（或 `python scripts/init_db.py`） |
| 任务状态（PowerContext） | 删除 `.state/powercontext-scope.json` 后重新 `state init`，或直接新建一个 `--task-id` |
| MiniMax 记录 | `docs/minimax/` 下的文件只是记录，删除不会影响代码；重新跑 `scripts/minimax_change.py` 会生成新记录 |

## 9. 说明

- 本样例的「测试集」在修改前后完全一致；MiniMax 只被允许修改 `workdir/biz/` 下的源文件，
  脚本会拒绝任何对 `workdir/tests/` 的改动（见 `scripts/minimax_change.py::_validate_files`）。
- 目标测试里的组合断言用「从种子数据独立计算期望集合」的写法（`_expected_ids`），
  避免出现「实现和预期一起写错」的自证问题。
