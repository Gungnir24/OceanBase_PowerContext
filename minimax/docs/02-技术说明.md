# 技术说明（一页）

## 一句话

把「规格、代码、测试、任务进展」变成一次可检索、可审计、可复现的上下文装配：规格按**适用面**做结构化命中选择，
按**文本相关性**做混合召回兜底，再用**锚点扩张**补全代码位置与测试用例；失效决策显式列出而不是悄悄丢掉。

## 为什么需要它

项目持续演进时，AI 助手最容易错的三件事是：

1. 拿到**已失效**的规格（旧的参数命名、被取代的 ADR）；
2. 只拿到规格文字，拿不到**该改哪个函数、该跑哪几个测试**；
3. 每次换会话就丢掉**上次改到哪、验证过什么**。

本模块针对性给出三件事：时效性过滤、来源定位（`path#symbol` / 测试函数）、任务状态复用。

## 总体流程

```text
data/specs/*.md ──解析条目──┐
workdir/**/*.py ──AST切分──┼─→ seekdb(documents/clauses/chunks/symbols) ──检索──┐
workdir/tests/**/*.py ──────┘                                                   │
                                                                                ├→ 上下文装配 → Markdown/JSON → MiniMax / Agent
PowerContext(scopes/memory) ──任务状态───────────────────────────────────────────┘
```

### 1. 资料入库（`ingest.py`）

- 规格按 `### <ID> <标题>` 切成**条目**，解析 `状态 / 适用 / 关联代码 / 关联测试 / 取代 / 正文`；
- 代码用 `ast` 切符号（`path#symbol`，方法记作 `Class.method`），同时抽可检索片段；
- 每个文档算摘要（digest），**内容没变就不重写**；文档被删除时清理其子行，保证幂等。

### 2. 召回（`retrieve.py`）

- 全文：`MATCH(body) AGAINST(...)`，分词器用 **ngram**（seekdb 上 `ik` 装了但召回为空，见限制）；
- 向量：`l2_distance(embedding, :q)` 精确扫描（seekdb 1.4.0 不支持向量索引）；
- 融合：RRF（K=60）合并两路排名，避免单路分数尺度不可比；
- 每次检索的通道、命中文件、分数、排名写入 `retrieval_logs`，可逐条复核。

### 3. 装配（`assemble.py`）

1. **结构化适用面**：从任务里识别接口（如 `/api/products`），取 `适用 = 该接口` 或 `适用 = 全局` 的**生效**条目 —— 这是精确命中；
2. **混合文本召回**：对任务文本检索规格片段，补充「适用面没写但内容相关」的条目；
3. **锚点扩张**：条目声明的 `关联代码` / `关联测试` 解析成 `path#symbol` 与测试函数，去 `symbols` 表定位行号；
4. **失效可见**：`已取代 / 已废弃` 的条目进 `excluded_specs`，并带上 `replaced_by`，让模型知道「这曾经这么写，现在不要」；
5. **预算裁剪**：超过 `max_bytes` 时先丢文本召回的片段、再截断片段正文，**规格条目与锚点永不丢弃**；
6. **悬空检测**：声明了但库里/磁盘上找不到的引用进 `diagnostics.missing_refs`，不静默失败；
7. **落库**：`context_runs` 存整份载荷与耗时，`retrieval_logs` 存命中明细。

### 4. 状态复用（`state.py` + `powercontext.py`）

- 一行一个事实：`[SDD][task=T-2026-1028][done] 实现 FILTER-001 ……`，`kind` 用 PowerContext 的 free-form kind；
- **PowerContext 是主存储**，本地 `task_states` 表只是镜像，用于 `db sql` 对账；
- 读取走 `POST /v1/memory/entries/list`，每次都是真实网络请求（`.state/powercontext-calls.jsonl` 留痕），
  所以「模块重启后还能读到」是结构保证，不是缓存巧合；
- `context/prepare` 用来给「下一步该做什么」提供一个有界摘要；
- `verify` 把测试日志正文作为 Source 存进 PowerContext，验证结论可追溯。

## 存储分工（为什么不是只用一个库）

| | seekdb | PowerContext |
| --- | --- | --- |
| 存什么 | 项目事实（规格条目、代码符号、测试清单、检索审计） | 任务事实（进展、决策、验证结果） |
| 谁变 | 项目演进时整体重导入 | 每个任务、每次会话增量追加 |
| 查询方式 | SQL（结构化 + 全文 + 向量） | REST（按 scope/task 列条目 + 有界上下文） |

一句话：**seekdb 回答「项目现在是什么样」，PowerContext 回答「这个任务做到哪了」。**

## 与 MiniMax 的接口

- `context.json.markdown` 直接进系统提示词，规格用条目编号、代码用 `path#symbol`、测试用文件+函数名；
- 要求模型输出**整文件 JSON**（`{analysis, files:[{path,content}], notes}`），而不是 diff：
  规避 patch 上下文不匹配的失败模式；脚本侧再生成标准 diff 存 `data/patches/`；
- 硬约束写在提示词里并由脚本二次校验：只能改 `workdir/biz/**`、禁止碰测试、禁止新增文件、禁止第三方依赖；
- 失败重试是「回滚基线 → 带上 pytest 失败摘要 → 重喊一轮」，最多 3 轮，每轮原文落盘。

## 可复现性设计

- 检索用**确定性哈希向量**（blake2b 派生，384 维归一化），同样的输入永远同样的排名；
- MiniMax 的随机性不进主链路：提交的代码由 `applied-digests.json` 的 sha256 锁定，
  `scripts/replay_minimax.py --check` 可在不调用模型的情况下验证「代码 == 当时模型输出」；
- 规格更新用 `scripts/spec_update_demo.py` 一键演示「改规格 → 重导入 → 上下文变化 → 恢复」。

## 已知限制

见 README 第 10 节；核心三条：向量无索引（暴力扫描）、哈希向量只有词面相关性、
PowerContext 单机无鉴权（生产需加 token/HTTPS）。
